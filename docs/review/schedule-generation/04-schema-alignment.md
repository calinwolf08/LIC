# Schema alignment: what the engine must change to match the current database

The engine predates most of the schedule-scoping, ownership, locking and override work (migrations 022–027). This document lists, table by table, what the current schema means and how generation must be updated to respect it. Column facts come from `src/lib/db/types.ts` and the migrations; behaviour facts from `02-findings-and-bugs.md`.

---

## 1. Schedule scoping (migrations 022, 023, 024)

| Table / column                                                                                                                   | Meaning today                                                                            | Engine today                                               | Required change                                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scheduling_periods.user_id`                                                                                                     | Owner of the schedule                                                                    | Ignored; creates periods with `user_id = NULL` (F-23)      | Never create periods from the generate route; require `user.active_schedule_id`.                                                                                                                                                                                                                                                            |
| `user.active_schedule_id`                                                                                                        | The one schedule the user is working in                                                  | Used only _after_ saving, to pick a period id              | Resolve first via `requireActiveScheduleId(locals)`; everything else keyed by it.                                                                                                                                                                                                                                                           |
| `scheduling_periods.start_date/end_date`                                                                                         | Range of the schedule                                                                    | Ignored; request body decides                              | Validate `startDate/endDate/regenerateFromDate ⊆ [start_date, end_date]`; default them from the schedule.                                                                                                                                                                                                                                   |
| `scheduling_periods.is_active`                                                                                                   | Legacy installation-wide flag                                                            | Fallback lookup + activation (F-23)                        | Stop reading/writing it from generation.                                                                                                                                                                                                                                                                                                    |
| `schedule_students`, `schedule_preceptors`, `schedule_clerkships`, `schedule_sites`, `schedule_health_systems`, `schedule_teams` | Membership of entities in a schedule (entities may be shared between a user's schedules) | Ignored; `SELECT * FROM students` etc. (F-02)              | Every loader joins through the junction for `scheduleId`. | `schedule_configurations`                                                                                                        | Links `clerkship_configurations` rows to schedules                                       | Ignored (and per-clerkship config is ignored anyway, F-08) | Decide whether config is per schedule or per clerkship. The junction suggests per schedule, but `ClerkshipSettingsService` looks up by `clerkship_id` only. Recommend: config belongs to the clerkship (simpler), drop `schedule_configurations`, and note it in the spec.                                                                  |
| `schedule_assignments` has **no** `schedule_id`                                                                                  | Ownership flows through `schedule_students`                                              | Deletes/reads by date only (F-02/F-04)                     | Either (a) always filter through `schedule_students`, or (b) **add `schedule_assignments.schedule_id`** (recommended — one indexed column, no join, unambiguous when a student is in two schedules with overlapping dates, which the junction design allows and which makes (a) wrong). Backfill from `schedule_students` in the migration. |

## 3. New table: `generation_runs` (recommended)

Needed for the Results page (F-25), the audit trail (F-24) and the preview/apply contract (F-12).

```sql
CREATE TABLE generation_runs (
  id            TEXT PRIMARY KEY,
  schedule_id   TEXT NOT NULL REFERENCES scheduling_periods(id) ON DELETE CASCADE,
  user_id       TEXT NOT NULL,
  created_at    TEXT NOT NULL,
  mode          TEXT NOT NULL,            -- full-reoptimize | minimal-change | completion
  preview       INTEGER NOT NULL DEFAULT 0,
  options_json  TEXT NOT NULL,            -- startDate, endDate, cutoff, bypassedConstraints
  plan_json     TEXT NOT NULL,            -- kept/deleted counts + ids
  result_json   TEXT NOT NULL,            -- unmetRequirements[], violations[], statistics, strategiesUsed
  success       INTEGER NOT NULL,
  duration_ms   INTEGER NOT NULL
);
CREATE INDEX idx_generation_runs_schedule ON generation_runs(schedule_id, created_at DESC);
```

`GET /api/schedule/summary` (or a new `GET /api/generate/runs/latest`) returns the last non-preview run for the active schedule; the Results page renders `violationStats`/suggestions from it. Add the Postgres baseline equivalent in the same migration (`migrations.equivalence.test.ts` will enforce parity).

Optional: `generation_run_assignments(run_id, assignment_id, tier, fallback_team_id)` if per-row provenance is wanted; otherwise put `run_id` on `schedule_assignments`.

## 6. Postgres parity

The Postgres baseline stores `is_available`, `locked`, `is_completed` etc. as `BOOLEAN`. Engine code compares with `= 1` / `=== 1` / `? 1 : 0` in many places (`StrategyContextBuilder`, `CapacityChecker`, `commitAssignments`, `resolveClerkshipConfiguration`). Kysely passes those literals through, so under Postgres `WHERE is_available = 1` fails (`operator does not exist: boolean = integer`) and `defaults.allow_fallbacks === 1` is always false because the driver returns `true`/`false`. Every engine query and flag comparison must go through the dialect adapter's boolean helpers (see `src/lib/db/dialects/types.ts`), and `test:pg` must include an engine run.

## 7. Types

Regenerate `src/lib/db/types.ts` after the migrations above (`npm run db:types`), then remove the `as any` casts in the engine (`selectFrom(tableName as any)`, `students as any`, `elective: any`) so schema drift becomes a compile error rather than a runtime surprise.
