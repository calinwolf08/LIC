# Implementation roadmap

Ordered so that each step is shippable on its own, the S1 defects go first, and every step lands with the tests from `06-test-coverage-plan.md` that prove it. Phase 1b delivers the Stage 1 parity work from `08-tier-parity-and-interop.md`; it does not depend on the engine refactor and is worth shipping to non-entitled users on its own. Effort is a rough size for one engineer familiar with the codebase. Follow `docs/spec/plan/GUIDELINES.md` for definition of done.

> **Note on 1.2 (F-26).** The roadmap originally proposed a migration that recreates the three global-defaults tables to change the `assignment_strategy` CHECK. SQLite cannot `ALTER` a CHECK, so that means an unsafe multi-table rebuild (create-copy-drop-rename) with `CURRENT_TIMESTAMP`/timestamp-default portability traps across the SQLite and Postgres dialects. It is also unnecessary: the existing CHECK already accepts `continuous_single`, the engine (`configurable-scheduling-engine.ts`) and `constraint-factory.ts` already default to `continuous_single`, and `TeamContinuityStrategy.canHandle` already treats `team_continuity`, `continuous_single` and `undefined` identically. The root cause of F-26 was that the UI/enum offered `team_continuity` — a value the CHECK **rejects** — as the default. The fix therefore standardises the whole app layer on `continuous_single` (the DB-accepted, engine-default value) and drops the dead `continuous_team` value from the UI, the `AssignmentStrategy` enum, `AssignmentStrategyLabels` and the global-defaults Zod schemas. The frozen migration CHECK is left as a harmless superset (it still lists `continuous_team`); nothing in the app writes that value. The deprecated `requirements.schemas.ts` override path retains `continuous_team` in its enum to avoid churning its test suite; it is not on the live generation path.

| #   | Work                                                                                                                                                                                                                                                                                                                                                           | Fixes                     | Size |

> **Note on Phase 2 scope.** 2.2, 2.3 and 2.4 are implemented. **2.2** replaces the never-run constraint loop with a `ProposalValidator` (`engine/proposal-validator.ts`) that runs every proposed generated day through the single `validateAssignmentCandidate` — hard violations block, soft ones are surfaced on the run and, when named in `bypassedConstraints` (Stage 1 codes), stamped on the row as `override_codes` with note `auto-generation bypass`. The dead constraint loop, the `ConstraintFactory` wiring, the unused `buildSchedulingContext` and the engine's `CapacityChecker` field are removed; the standalone constraint classes/`ConstraintFactory` remain as an untouched library (superseded, not deleted). **2.3** adds `planRegeneration()`, one keep/delete classification shared by preview and apply (deletion by id, after planning); minimal-change now preserves valid future rows. **2.4** re-enables the minimal-change and per-constraint-bypass controls in the regenerate dialog. **2.1** (the pure `GenerationSnapshot` loader that would replace per-call DB reads) is **deferred** as a performance/architecture refactor — F-02's tenant-scoping correctness already shipped in Phase 0, so 2.1 is no longer a correctness item; the validator currently reads per-proposal, which is correct but not yet batched.

## Sequencing notes

- 0.1–0.7 can ship as one PR ("generation is tenant-safe and counts correctly") with the dialog controls hidden. Nothing in it changes the UI beyond that.
- Phase 2.1 is the largest single change; land it behind the existing engine interface (`engine.schedule(...)`) so suites 02–15 keep passing unchanged, then delete the old context builders.
- Do not start Phase 3 before Phase 2: strategy improvements are unverifiable until the validator exists.
- Phase 1b can run in parallel with Phase 1 by a second engineer — it touches the assignment routes and Stage 1 UI, not the engine. Land 1b.3 before Phase 2.2 so the shared validator has one caller shape to satisfy, and 1b.1/1b.8 before 0.6's persistence work is considered done.
- If time is short, Phases 0, 1 and 1b plus their tests are the minimum: Phase 0 makes generation safe, Phase 1 makes it configurable, Phase 1b makes its output usable and gives Stage 1 the concepts it is already allowed to configure.
