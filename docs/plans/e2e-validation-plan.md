# End-to-end validation plan — whole-app user journeys

**Goal.** Prove, in a real browser against the built app, that every piece of the product fits together the way a coordinator uses it: identity → schedules → entities → manual scheduling → validation surfaces → calendar/export → (entitled) auto-generation → editing generated schedules → tier parity. Backend logic is already well covered (1 693 server tests, 20 browser component tests, 15 Postgres tests, the Phase-5 one-validator gate). What is _not_ proven today is that the API layer, the Svelte pages and the dialogs compose those services correctly across a long session — the seams where "works in isolation, breaks in combination" bugs live.

**Non-goals.** No "fill one field and click" tests. No re-testing engine arithmetic through the UI (that lives in `src/lib/features/scheduling/**`). No visual-regression snapshots.

This plan divides the work into eight phases. Each phase = **write journeys → run → triage failures → fix product bugs (with a unit/integration test) → re-run → close**. Phases 1–4 are Stage 1 and can proceed in parallel with 5–6 (Stage 2) once Phase 0 is done; Phase 7 combines areas and needs everything before it.

---

## 0. Ground rules for every journey

1. **A journey is an arc, not an action.** Minimum shape: set up ≥3 entities through the UI (or seeded), perform ≥4 dependent user actions, assert at each step, end in a state that a later step depends on. If a test can be described as "open X, click Y, see Z" it belongs in a component test, not here.
2. **Assert on three layers at key checkpoints.** (a) what the user sees (role/label/testid), (b) what the API says (`page.request.get(...)` in the same session — same cookies, same tenant), (c) where it matters, what the DB holds (`getTestDb()` from `e2e/test-db.ts` — `source`, `override_codes`, `locked`, `elective_id`, `schedule_id`). A UI that shows the right thing over wrong data is a bug this plan must catch.
3. **Both tiers, on purpose.** Every Stage 1 journey has a variant tag: `@both` (run as `admin` _and_ `basic`), `@stage1-only` or `@stage2-only`. Over-gating (a basic user losing manual features) is as much a defect as under-gating.
4. **Deterministic data.** All dates via `fromToday()` / `monthStart()` from `seed-schedule.ts`. Unique names via a per-test stamp. Every journey that changes the active schedule or seeded rows restores them in `afterEach` (pattern already in `end-to-end.spec.ts`).
5. **Real auth, real server.** Log in through the form (`login()`), never a bypass. The `webServer` builds and previews a fresh, seeded SQLite DB (`playwright.config.ts`), and `reuseExistingServer` is off in CI.
6. **No timers.** Wait on hydration signals (`form[data-hydrated]`), on `expect(...).toBeVisible`, on URL changes, on option counts — as the current helpers do.
7. **Edge cases are folded into the arc**, not split into micro-tests: the same journey that creates the clean assignment also hits the double-book, the blackout, the capacity limit, and the past-date warning on its way.
8. **A failure is a finding.** Triage each into one of: **product bug** (fix in the same phase + regression unit test), **testability gap** (add a `data-testid`/`aria-label`, never a sleep), **spec ambiguity** (decide, record in `PRODUCT_SPEC.md`, then assert). No `test.fixme` survives a phase close.

### 1.2 Gaps and inconsistencies found while surveying (fix or decide in the phase that owns them)

- **Swap has no UI.** `POST /api/schedules/assignments/swap` exists and is parity-tested, but no Svelte file references swap. **Decision (Phase 3):** keep the route and service — they are correct and atomically validated — but do **not** wire a UI for now; revisit only if coordinators ask to trade two assignments' preceptors. J3.6 covers the route at the API level so it cannot rot. (finding P3-e)
- **Capacity rules and fallbacks have no UI of their own**; they are reachable only through the clerkship "Auto-scheduling" settings. Phase 5 tests them there and records the decision.
- **`/students/[id]/edit` route exists** though spec §6 says editing is inline on the detail page. Phase 2 asserts the inline path and decides whether the route is a redirect or dead.
- **Two helper layers**: `e2e/helpers.ts` + `e2e/utils/*` (older, mostly unused) vs `e2e/journeys/helpers.ts` + `assignment-helpers.ts` (current). Phase 0 consolidates.
- **`@playwright/test` is `^1.49.1` in `package.json`; 1.56.1 is installed** and matches the pre-installed Chromium (1194). Pin the exact version in Phase 0 so CI and local agree.
- **Seed is rich but static**: no electives on any clerkship, every student onboarded everywhere, no blackout dates, no locked or generated rows, no team-less clerkship. Phase 0 extends it (06 §5) so journeys do not have to build these from scratch every time.
- **Blackout dates are global, not per tenant.** `blackout_dates` has only `id`, `date`, `reason` — no schedule or owner column — so a blackout added by tenant B flags tenant A's assignments and shows on A's calendar. This is a tenant-isolation defect (F-02 family) to fix in Phase 4 (J4.2) with a `schedule_id` (or `user_id`) column and scoped queries; until then the seed adds blackout dates only once, and `snapshotTenant` deliberately excludes them.
- **`e2e/global-setup.ts`** only opens the DB; nothing verifies seeded invariants before the run. Add an assertion pass (user exists, entitlement set, availability materialised) so a broken seed fails fast rather than as 40 red journeys.

## 2. Phase 0 — Journey infrastructure (prerequisite for everything)

**Deliverables**

1. **Fixtures** (`e2e/fixtures/`):
   - `users.ts`: `asAdmin`, `asBasic`, `asFreshUser` fixtures that log in once per worker and reuse `storageState`; `asFreshEntitledUser` = register, then grant `autogen` via `setEntitlement(email, ['autogen'])` (DB write through `getTestDb()`) and re-login.
   - `sandboxSchedule` fixture: creates a short schedule via API, switches into it, restores the seeded active schedule and deletes the sandbox after the test (generalises the pattern in `end-to-end.spec.ts`). Every mutating journey runs inside one, so sibling specs never see each other's rows.
   - `api(page)`: thin typed wrapper over `page.request` returning `{ ok, status, data, error }`, so journeys can assert envelope shapes uniformly.
   - `db.ts`: `rowsFor(scheduleId)`, `assignment(id)`, `setEntitlement`, `grantEntitlement/revokeEntitlement`, `snapshotTenant(userEmail)` (ids + counts for the tenant-isolation before/after diff).
2. **Page objects** for the seams every journey touches: `AssignmentDialog` (extends `assignment-helpers.ts` with range selection, elective picker, lock checkbox, site select, override branch selection by label), `HealthPanel` (counts by type, override list, include-resolved), `CalendarPage` (view switch, filters, day click, export trigger returning the response), `EntityTabs`, `ConfirmDialog`.
3. **Seed extensions** (`seed.ts` / `seed-demo.ts`, 06 §5): one required (3-day) and one optional elective on _Internal Medicine_ with preceptor and site pools; leave one seeded student **un**-onboarded at _Community Care Partners_; two blackout dates inside the schedule range; one locked manual row; _Psychiatry_ with **no** team (drives the no-team eligibility rule); a Tenant B blackout date and team so isolation can be proven for those too.
4. **Testability hooks** (add `data-testid` where journeys will otherwise need brittle text matching): calendar day cells (`cal-day-YYYY-MM-DD`), assignment chips carrying `data-source` / `data-locked` / `data-elective`, list-row status pills (`student-status`, `preceptor-availability-configured`), dashboard cards, results-page cards, readiness checklist items (`readiness-<id>`), sidebar switcher.
5. **Suite mechanics**: exact-pin Playwright; tags via `test.describe` annotations (`@smoke`, `@stage1`, `@stage2`, `@tenant`, `@long`); `retries: 0` for new journeys in CI (flakes are bugs), `trace: 'retain-on-failure'`, `video: 'retain-on-failure'`; CI matrix shards by tag; `global-setup` invariant assertions; delete `e2e/helpers.ts` + `e2e/utils/` after migrating the two things still used.

**Definition of done.** Existing 49 tests green on the new fixtures; a `@smoke` subset (fresh-signup, end-to-end, gating, tenant reads) runs in < 4 minutes; `npm run test:e2e -- --grep @smoke` documented in `README`.
